
# 2508.13678v1 — Blocked Sparsity, Quantization Interactions & Profiling Instrumentation

## Part 1: Blocked Sparsity + Quantization Interactions

TL;DR

- Interaction effects between blocked sparsity and quantization on CPU inference latency and accuracy; practical heuristics and microbenchmarks provided.

Why it matters

- Blocked sparsity and quantization are promising for CPU inference. Understanding their interaction helps design cache-friendly kernels and mixed-precision policies for lightbulb.

Key takeaways

- Block sizes and quantization granularity interact: smaller blocks favor cache locality but increase metadata overhead.
- Quantization noise can amplify when sparsity removes calibration data; per-block calibration recommended.
- Simple fusion strategies (quantize-then-sparsify or sparsify-then-quantize) show different trade-offs; authors benchmark both.

Implementation steps

1. Reproduce the authors' microbenchmarks on small CPU cores (use provided matrix sizes).
2. Add a blocked-sparsity kernel to `lightbulb::kernels` with configurable block size and quant-aware accumulation.
3. Implement per-block calibration hooks and a small profiler to select block+quant pairs.

Acceptance criteria

- Microbenchmarks reproduce reported latency trends within 10% on target CPU.
- Kernel exposes block size and quantization policy and a simple heuristic to pick defaults.

## Part 2: Profiling Attention Memory Peaks & Instrumentation Hooks

TL;DR

This work introduces a lightweight profiling method to estimate per-layer attention memory peaks and suggests tooling-friendly instrumentation hooks.

Why it matters for lightbulb

- Instrumentation hooks are necessary for `KvPager` and `Scheduler` to make live decisions; these profiling ideas give low-overhead signals we can use.

Actions

1. Add a small profiling helper in `engine` that reports per-layer peak working set for synthetic runs.
2. Document instrumentation hooks in `docs/benchmarks/instrumentation.md`.

Acceptance criteria
