
# 2501.09223v2 — Latent-space Routing / Lightweight Router

TL;DR

Describes a compact latent-space router for conditional compute that routes tokens to small expert sets using a lightweight projector and top-k selection, reducing routing overhead compared to MoE baselines. Routing decisions are made in a compact latent space (short context summaries) to select small expert modules, minimizing decision latency and communication cost while preserving per-request quality.

Why it matters for Lightbulb

- Low-overhead routing is essential for CPU-bound MoE or conditional compute approaches where routing costs can negate compute savings.
- A lightweight router helps enable conditional compute paths with low overhead, which is critical for per-request latency targets and for scaling capacity-aware MoE behaviors on CPU-centric stacks.
- The design informs our Router module: a small projector, budgeted top-k, and lazy expert activation.

Key technical takeaways

1. A small dense projector (few hidden dims) suffices to produce routing scores that rank experts well; routing compute can be <1% of total model FLOPs if kept compact.
2. Top-k routing with budget enforcement reduces load imbalance while limiting memory touches.
3. Lazy expert activation (delay materializing expert weights until needed) significantly reduces memory bandwidth costs for sparse workloads.
4. Routing metrics (entropy, top-k score gap) are useful signals for adaptive router hyperparameters.

Actions / Implementation steps for lightbulb

1. Implement a thin-router prototype: small MLP projector, softmax/top-k selection, and scoring telemetry.
2. Implement budgeted top-k and a load-balancer fallback that rebalances tokens across experts when imbalance grows.
3. Add lazy-activation support at the loader/kernel boundary so expert weights are touched only on demand.
4. Instrument routing telemetry (latency, load imbalance, routing entropy) and expose in tracing/logs.
5. Implement a `engine::Router` trait sketch and a simple softmax-based router that can be plugged into the scheduler for experiments.
6. Add a microbenchmark in `bench/` that measures routing decision latency and routing accuracy vs an oracle routing label set.
7. Add a ROADMAP note describing when to prefer latent-space routing vs heavier MoE routing (cost thresholds, request sizes).

Acceptance criteria

- Router prototype shows routing latency <5% of expert compute time and measurable end-to-end throughput gains on synthetic sparse workloads.
- Routing telemetry is exposed and testable under continuous integration.
- `engine::Router` trait added with a working softmax router and unit tests.
- Microbench demonstrating routing overhead <5% added latency on a toy model, or a documented decision to defer prototyping.
