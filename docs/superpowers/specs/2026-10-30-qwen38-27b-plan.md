## The target

From `Qwen/Qwen3.8-27B/config.json` (Apache-2.0, `model_type: qwen3_5`, arch `Qwen3_5ForConditionalGeneration`, a multimodal wrapper; the text tower is what Lightbulb serves):

| Field | Value |
|---|---|
| layers / pattern | 64; `full_attention_interval` 4: 3 Gated DeltaNet then 1 full attention, so **48 Gated DeltaNet + 16 full attention** |
| hidden / MLP | 5120 / 17408 (SwiGLU) |
| full attention | 24 heads, 4 KV heads, head_dim 256, output gate, partial rotary 0.25, mrope |
| Gated DeltaNet | 16 key heads x 128, 48 value heads x 128, conv kernel 4, `mamba_ssm_dtype` float32 |
| vocab / context | 248320 / 262144 |
| extras not needed for text | vision tower (27 deep), 1 MTP layer |

Quantized files exist: `unsloth/Qwen3.8-27B-GGUF` (6.2M downloads on the Hub today) has `UD-Q4_K_M` 16,464,440,224 B (15.33 GiB), `Q4_0` 16.06 GB, `UD-IQ4_XS` 14.25 GB, `UD-Q3_K_XL` 13.15 GB, `Q8_0` 29.05 GB. Ollama reports the architecture of the 9B/4B Qwen3.5/3.8 GGUFs as `qwen35`; llama.cpp's `gguf-py/gguf/constants.py` names `qwen35`, `qwen35moe` and `qwen3next`, with tensors such as `blk.N.ssm_conv1d`, `ssm_a`, `ssm_dt`, `ssm_alpha`, `ssm_beta`, `ssm_norm`, `ssm_out`, `attn_qkv`, `attn_gate`. I did not read the per-architecture tensor list or a 27B file's metadata (**unverified**).

**Consequence: no multi-GPU split is needed for the first run.** The 15.33 GiB Q4_K_M plus KV and state fits one 24 GB P40 or the 32 GB MI50, so the first target is **a single P40 through CUDA**, then the MI50, then the Vulkan cards. Pipeline-split (D4) leaves the critical path (still wanted later for models larger than one card). What stays: `device::select` must **enumerate mixed vendors on one box** (CUDA devices plus Vulkan devices), choose one deliberately, and the B9/B17 preflight must run **per device**, against the device actually chosen. Both operating systems are in scope (dual boot, Windows and Linux).

### What differs between Windows and Linux (items marked unverified come from general knowledge, not from this rig)

| Area | Difference |
|---|---|
| NVIDIA P40 | Windows can run it in WDDM or TCC mode (TCC is compute-only and reserves less VRAM); Linux has no such split. The P40 has no display output. Pascal's fp16 rate is very low, so an f32 or quantized path is the right one (**unverified for Fuel's kernels**) |
| CUDA build | Windows builds go through `cuda-build.ps1` here; Linux needs a CUDA toolkit and a matching driver. Both need Fuel's kernels compiled for sm_61 (**unverified**) |
| Vulkan | Windows: vendor ICDs behind `vulkan-1.dll`; Linux: ICD files, Mesa RADV for AMD and ANV for Intel, NVIDIA's own driver. The same GPU can report different memory heaps and limits under each (**unverified**) |
| AMD gfx906 (Radeon VII, MI50) | Linux ROCm support for gfx906 is deprecated or removed in recent releases and the Windows HIP SDK does not list it (**unverified**), so Vulkan is the dependable AMD path on both |
| Device memory query | The VRAM-return probe and the gpu-run lock use `nvidia-smi` on Windows; per-device free memory otherwise comes through Fuel's `BackendRuntime::available_bytes`, untested on Vulkan |
| Model files | Models directory, path separators and mmap behaviour differ; a GGUF is read through a memory map, which interacts differently with each page cache |
| Measurement tooling | `gpu-run.ps1` (the machine lock) is PowerShell; Linux runs need an equivalent lock before any shared-GPU measurement |
| Dual boot | One OS runs at a time, so each needs its own build and measurements; numbers from one are not evidence about the other |

## Memory arithmetic (computed)

- **Weights:** Q4_K_M is 15.33 GiB. It does not fit a 16 GiB card with any KV or workspace (Radeon VII, A770) but **fits one 24 GB P40 or the 32 GB MI50**, leaving about 8 GiB (P40) or 16 GiB (MI50) for KV (2 GiB per 32k tokens at f16), the 144 MiB per-sequence state and workspace. This holds only once the weights stay quantized (next bullets).
- **KV (16 full-attention layers only):** 16 x 4 heads x 256 x 2 (K,V) = 32768 values per token: **64 KiB/token at f16, 128 KiB at f32**. 32k context = 2 GiB (f16) / 4 GiB (f32); 128k f16 = 8 GiB.
- **Gated DeltaNet state:** per layer 48 x 128 x 128 x 4 B = 3 MiB, x 48 layers = **144 MiB per sequence, constant in context length** (f32 by Fuel's own note), plus a small conv state (kernel 4, 10240 channels). Per-session, not per-token.
- **Embedding hazard:** Fuel's row 40 says the token embedding is held as f32: 248320 x 5120 x 4 B = **4.74 GiB**, which is a third of a card. Must not happen for a quantized run.
- **GGUF weights are dequantized to f32 on load (answered by Fuel, 2026-10-30, PR #530 audit).** `QuantizedLlama3Model::from_gguf` keeps only `Q4_0` quantized; every other GGML dtype (f16, Q8_0, Q4_K_M, Q6_K) is dequantized to f32 at load (`lazy_quantized_llama.rs`, `match dt {Q4_0 => .., _ => dequant_bytes_to_f32}`), and `WeightStorage` has only F32/BF16/Q4_0/Awq. That is why my VRAM probe saw the same footprint for f16 and Q8_0. **Consequence: a 27B Q4_K_M would become about 108 GB of f32 today, so nothing in this plan can run until K-quants stay quantized end to end (Fuel row 124, on the critical path).** It also means the B9 preflight's on-disk size is a far-too-low estimate on this path (about 4x for Q4_K_M): see ROADMAP B17.
- **B9 preflight** compares to one device's free memory. B17 (PR #273) makes it use resident bytes for a GGUF. Today a 27B Q4_K_M is about 108 GB resident, so the B17 estimate refuses it on every card here, correctly, until Fuel row 124 lands; after row 124 the on-disk figure is right again and the estimate must be deleted.

## What Lightbulb must build (after Fuel provides the model)

| # | Lightbulb work | Notes |
|---|---|---|
| L1 | `qwen35` arch dispatch and `loader_gguf_qwen35.rs` (config from GGUF metadata, tokenizer with a 248k vocab, EOS ids), like `loader_gguf_qwen3.rs` | `detect_architecture` (`gguf/mod.rs:1732`) refuses everything but `llama`/`qwen3` today |
| L2 | **Mixed-vendor device enumeration and selection** (CUDA and Vulkan devices on one box; an explicit choice by index or name, default the one the model fits), later multi-device groups | `device.rs` is CUDA-or-CPU. The first target needs only CUDA on the P40; Vulkan (F6) comes after Fuel row 124 |
| L3 | B9/B17 preflight **per device**, against the device actually selected (resident weights + KV + f32 state), later against a placement plan | the GPU/CPU refuse-or-warn rule and the override stay |
| L4 | Scheduler/KV budget for a hybrid model: `KvBudget{block_size,num_blocks}` assumes KV for every layer; here KV exists for 16 of 64 layers and each session also holds fixed state | Lightbulb's mirror scheduler (B8b) would also be wrong |
| L5 | Prefix sharing OFF for hybrid models (splicing KV blocks cannot restore recurrent state at the prefix boundary without a state snapshot) | already off by default; make it a refusal for hybrids |
| L6 | Chat template and tool-call format for Qwen3.8 (thinking tags, tools) through the existing minijinja resolver; A4 per-family parser | verify against the model's real template |
| L7 | Tests: Fuel's oracle target is `Qwen/Qwen3.5-0.8B` (24 layers, 18 + 6); add its GGUF to the corpus and a census row; golden logits vs an answer key | only 0.8B can run without the rig |
| L8 | Multi-model/F2 unload (VRAM release) is NOT needed for the first run | see the F2 design |

## Sequence and gates

1. **G0:** CireSnave confirms the rig (cards, VRAM, OS). Fuel answers D1-D6 (owner, order, release).
2. **G1:** Fuel stage 2 produces correct logits for Qwen3.5-0.8B (CPU first). Lightbulb meanwhile can do L2/L3/L4 design and the Vulkan device-selection groundwork, which depend on nothing in the model.
3. **G2:** quantized `qwen35` GGUF loads and decodes 0.8B on CPU through Lightbulb (L1, L5, L6, L7), measured against the answer key.
4. **G3:** 0.8B on CUDA (the P40 or the 4060). **G4:** 27B Q4_K_M on one P40, measured (TTFT, tok/s, VRAM), the preflight accepting it without the override; then the MI50 (Vulkan) and the other cards; then the same on the other operating system.

Nothing here is on the critical path of a Lightbulb-only change until D1-D3 exist. The long pole is Fuel: **K-quants staying quantized (124) comes first**, then D1, D3, D4. Fuel's answer, 2026-10-30: none of it is built, owner Fuel 1, unscheduled until the PM rules the rows.
